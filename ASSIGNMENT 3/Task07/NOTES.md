# Q7 – Concurrent, fault-tolerant result processor

Design: one independent `Callable` per score file; a fixed `ExecutorService` bounds concurrency; each task returns a success/failure `Outcome`; the coordinator collects every `Future` and stores outcomes in a `ConcurrentHashMap`. One corrupt file becomes a failure outcome and does not cancel other tasks. The program measures pool sizes 1, 2, 4 and 8. It creates eight valid files and one corrupt file for a repeatable demonstration.

Expected correctness invariant: total outcomes = successes + failures, and every discovered input file has exactly one outcome. For 10,000 files and p workers, idealized processing time is approximately total work/p when CPU-bound, but I/O contention and scheduling overhead may reduce gains. Memory is O(n) for futures/results; worker thread stack memory is O(p × stack size). One-thread-per-file uses O(n) threads/stacks and risks resource exhaustion. Parallel streams use the common ForkJoinPool and offer less explicit lifecycle/control. Missing files must be included in a manifest of expected filenames if they need to be counted as failures; directory listing alone cannot discover absent paths. The current sample handles files that exist but are corrupt/unreadable.
