# Q5 – Race conditions and synchronization

The required synchronized method makes the check-and-set plus counter increment one atomic critical section under the object's intrinsic monitor. Expected output includes `Seats sold: 10`. A synchronized block can lock only the critical section: `synchronized (this) { ... }`. An unsynchronized check-then-act is a data race; multiple threads may observe `false` before any writes `true`. The included barrier-based unsafe example intentionally aligns competing reads to make the race visible; it is an illustration, not a production booking implementation.

For a cinema with multiple screens, use a per-screen or per-seat lock/atomic state to reduce unrelated contention, while ensuring seat identity is globally unambiguous. Static synchronization is needed only when coordinating shared static state across all instances. An AtomicBoolean per seat with compareAndSet(false,true) is suitable for independent seats. ReentrantLock supports timed/interruptible acquisition. A ConcurrentHashMap can use putIfAbsent for seat identifiers. Each approach needs O(s) state for s seats; booking is expected O(1), with contention-dependent waiting.
